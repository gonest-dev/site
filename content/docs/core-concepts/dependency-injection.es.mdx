gonest resuelve las dependencias por **tipo**, no por nombre o token de cadena.

## `owner.Inject[T]()`

Resuelve exactamente una instancia de `T`. Da panic si se encuentran cero o más de una
coincidencia.

- **Tipos de puntero** (`*UserService`) requieren una coincidencia exacta de tipo.
- **Tipos de interfaz** también requieren una coincidencia exacta — ya no existe una alternativa
  estructural. Un Provider solo se vuelve resoluble por una interfaz `T` si fue envuelto
  explícitamente para `T` vía `ref.As[T]()`; consulta
  [Exportando un Provider como una interfaz](/docs/core-concepts/providers#exportando-un-provider-como-una-interfaz).

```go
userService := controller.Inject[*UserService]()
```

## `owner.InjectAll[T]()`

Resuelve **cada** Provider que coincide con `T`. Nunca da panic en 0 o N coincidencias — úsalo
para patrones de plugin/estrategia (plugin/strategy patterns) donde múltiples Providers implementan legítimamente
la misma interfaz.

```go
type Pingable interface {
  Name() string
  Ping(ctx context.Context) error
}

var HealthController_ = gonest.NewController(func(controller *gonest.Controller) {
  controller.Path("/health")
  pingables := controller.InjectAll[Pingable]()
  _ = pingables
})
```

<Callout type="info">
  Este es el mismo patrón utilizado para [Health Checks](/docs/health-checks): cualquier
  número de servicios puede implementar `Pingable`, y el Controller de salud los
  descubre todos automáticamente.
</Callout>

## Dónde se puede llamar a `Inject`

`Inject`/`InjectAll` son legales dentro de los constructores de `Provider`, `Controller`
— en cualquier lugar donde el framework garantice que la Fase 1 (resolución de Providers) ya
se ha completado. Consulta [Bootstrap](/docs/getting-started/bootstrap).

Desde un owner `Provider`, `owner.InjectAll[T]()` resuelve de forma distinta a como lo
hace desde un owner `Controller`/`Middleware`/`Guard`/`Interceptor`/`Filter`. El constructor
(builder fn) de un `Provider` corre antes de que exista cualquier instancia, así que, en vez
de resolver de inmediato, `InjectAll` devuelve ya mismo un slice de longitud fija — ya
dimensionado según cuántos Providers en el alcance coinciden con `T` — y cada elemento se
completa in situ tan pronto como su Provider correspondiente realmente se resuelve. Solo los
Providers `gonest.ScopeSingleton` pueden ser miembros de ese slice: un Provider
`ScopeTransient` que de otro modo coincidiría hace que `NewApp`/`NewApp` lance panic. El
orden de los elementos del slice no está garantizado, y cero coincidencias sigue devolviendo
un slice vacío en vez de panic — el mismo contrato que el camino de resolución directa de
arriba.

Los constructores de `Guard` son la única excepción: **no** tienen soporte para `Inject`,
porque un solo Guard se puede adjuntar a través de múltiples Controllers/Modules —
no hay un único "propietario" (owner) con el cual resolver.

## Builder fn, no `Constructor`

`Inject`/`InjectAll` deben llamarse en el **builder fn** — la función pasada a
`gonest.NewProvider`/`NewController`/etc — **antes** de que `Constructor(...)` se registre,
nunca desde dentro del propio closure de `Constructor`:

```go
var UserService_ = gonest.NewProvider(func(p *gonest.Provider) {
  // ✅ correcto: resuelto aquí, en el builder fn
  repo := p.Inject[*UserRepository]()

  p.Constructor(func() *UserService {
    // ❌ incorrecto: llamando a MustInject/MustInjectAll DENTRO de Constructor
    // repo := p.Inject[*UserRepository]()
    return &UserService{repo: repo}
  })
})
```

El builder fn de un `Provider` corre durante la Fase 2 (Declare), antes de que la Fase 3
construya su grafo de dependencias o invoque un solo `Constructor`. Llamarlo correctamente ahí
permite que la Fase 3 resuelva la dependencia y la complete antes de que `Constructor` siquiera
corra. Llamarlo desde dentro de `Constructor` en cambio significa que la Fase 3 ya está
corriendo — el grafo de dependencias ya está construido, cada goroutine ya fue despachada — así
que la llamada llega demasiado tarde para que algo la consulte. `NewApp`/`New` ahora lanza panic
con un mensaje que nombra el tipo exacto (`gonest: MustInject[T] called from inside a
Constructor — ...`) si esto ocurre, así que el error aparece de inmediato en el bootstrap en
lugar de dejar una dependencia permanentemente en valor cero sin ningún error en ningún lado.
